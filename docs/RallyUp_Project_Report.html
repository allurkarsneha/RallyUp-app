1. Executive Summary

RallyUp is a Flutter mobile application backed by Firebase that helps amateur sports players discover each other, reserve courts, organise open matches, and chat — all in a single integrated experience. The project ships 30,000+ lines of production-shaped Dart across 143 files, ten live Firestore collections, transactional Firestore writes for concurrency-sensitive operations, real-time direct and group chat, push notifications wired to a Firebase Cloud Function, an in-app admin moderation surface, and shared schedule-conflict prevention that spans bookings, open matches, invites, and joins.

The app exists because existing tools split this work across three places — court-booking apps, generic messaging apps, and sports-pickup apps — none of which share a real schedule or contact graph. RallyUp puts booking, messaging, invites, and notifications inside one consistent Firebase-backed model so a single tap can take a user from "I'd like to play tennis Saturday" to "court reserved, three friends invited, group chat ready."

2. Problem Statement & Goals

Problem

Amateur players today rely on a fragmented toolchain: a court-booking app for the venue, WhatsApp groups for organising who shows up, and DMs to invite individual players. These three planes don't share a single source of truth, so:

  • It is easy to double-book yourself across two different courts at the same time.
  • A host's "open match" lives only as a verbal commitment; players who join late have no record.
  • Cancellation propagation is manual — when a host cancels, the venue, the group chat, and the personal invites all need to be touched separately.
  • Trust between strangers is hard to build because no system carries identity, history, or moderation between meetups.

Goals

  • One app where booking, hosting, inviting, joining, and chatting all share one data model.
  • Real concurrency safety: no two users can join the last spot of a match.
  • Real schedule safety: a user cannot be in two overlapping sessions even at different courts.
  • A live group chat per open match, automatically populated, automatically cleaned up.
  • Honest notifications: every state change that affects another user surfaces in their bell and (eventually) on their lock screen.
  • Project-appropriate trust signals: profile-level visibility, optional ID verification, "report user" path.

3. Feature Overview

3.1 Onboarding & Authentication

  • Email + password sign-up and sign-in via Firebase Authentication.
  • Multi-step onboarding wizard: name, email/phone, photo, sports preferences, location.
  • Profile photo capture from camera or library, uploaded to Cloudinary.
  • Optional GPS location capture at first run, with manual city picker fallback.
  • Forgot-password flow on the login screen and inside Account Settings → Privacy.
  • Account deletion with the auth-first invariant — Firebase Auth deletes first, local state clears after.

3.2 Profile

  • Display name, profile photo (Cloudinary URL, curated avatar id, or initials), bio, age, postal code, sports, weekly availability, location.
  • Profile-visibility toggle that hides the user from discovery surfaces.
  • Editable avatar, sports list, and availability.
  • Optional ID verification submission (document + selfie) reviewed inside the app by an admin.

3.3 Courts

  • Streamed list of courts from courts/{id}, debug-only seeded at startup.
  • Per-court details page with an image carousel.
  • Sport, search, and sort filters (default, distance, rating, lowest price).
  • Distance + same-city ranking computed via haversine from the user's stored location.
  • Court images are Cloudinary URLs; null/empty/error states fall back to a placeholder.

3.4 Private bookings

  • Book Court sheet picks sport, date, 1-hour slot, and match type.
  • Confirm Booking page reviews the draft and writes the bookings/{id} doc on confirmation.
  • Past-time slots auto-hide; occupied slots disappear via the availability service.
  • My Bookings shows Upcoming / Past tabs with tags: Confirmed / In progress / Completed / Cancelled.
  • Soft-cancel from My Bookings via the 3-dot menu.

3.5 Open matches

  • Hosts create an open match through PlayersSetupSheet, setting players required and already-confirmed guests.
  • Two parallel-array player lists (joinedPlayerIds, joinedPlayerNames) plus an integer confirmedGuestCount.
  • Atomic join via Firestore transaction — cancelled, full, host-self-join, and duplicate are all caught.
  • Leave (joined player) and Cancel (host) are both transactional.
  • Host cancel auto-notifies joined players and cancels every pending invite.
  • Public lists hide cancelled, full, past, host's own, and already-joined matches.

3.6 Invites

  • Unified Invites page with Sent / Received tabs (initial tab decided at push time).
  • Host opens a player's profile → Invite → picker shows only their hosted matches still actionable for that invitee.
  • Invite docs at invites/{id} carry court, date, time, and pinned avatar/name snapshots for both sides.
  • Live "X / Y joined · N spots left" line on every invite card streams the underlying match.
  • Host cancellation auto-cancels pending invites and fires a "Match cancelled" notification to each invitee.

3.7 Notifications

  • Per-user notifications/{id} collection with ten typed events.
  • Notifications bell with unread badge.
  • Tap routing per targetType: booking → BookingConfirmedPage; match → MatchDetailsPage; pending invite → Received tab; resolved invite → MatchDetailsPage.
  • Empty + error states; "Mark all read" action.

3.8 Messages

  • Direct 1-to-1 chat with deterministic thread id uidA_uidB (sorted).
  • Group chat per open match with deterministic thread id match_<matchId>.
  • Single threads/{threadId} collection with a type: 'direct' | 'group' discriminator.
  • Three tabs: All (direct only), Unread (direct + group filtered to unread), Groups.
  • Per-user lastReadAtByUser map; opening the chat is the only path that bumps the read marker.
  • Group chat auto-creates on match create; joiners are auto-added via arrayUnion; leavers auto-removed via arrayRemove.

3.9 Feedback & Moderation

  • Feedback & Suggestions submits to feedback/{id}.
  • Player profile → ⋮ → Report user writes to reports/{id}.
  • Admin-only ID verification review queue gated by allow-listed admin emails; approve / reject with reviewer note.

3.10 Legal

  • Real readable Privacy Policy and Terms of Service pages with eight sections each (last updated May 30, 2026).

State management

The project uses Provider with two ChangeNotifiers: AuthProvider (current user, status, profile updates, password reset) and SignupFormProvider (multi-step onboarding form data). All other screens consume Firestore streams directly via StreamBuilder, so state is push-driven by the database rather than held in client-side stores.

Navigation

The shell pattern: a single MaterialApp hosts AuthGate as its home; the gate decides between Onboarding/Login and MainShell. MainShell owns the bottom nav and holds three tabs (Home, Messages, Profile) in an IndexedStack so tab state is preserved across switches. Pushed routes (Courts, Match Details, Profile editors, etc.) live above the shell; they never replace it. A helper switchToMainShellTab(context, index) pops back to the shell and flips its active tab from anywhere in the app without rebuilding it.

Query patterns

All queries are intentionally single-field equality (where('userId', isEqualTo: …), where('hostUid', isEqualTo: …), etc.) or arrayContains; client-side sorting + filtering finishes the job. This avoids composite indexes at the current scale and keeps the project deployable from a clean Firebase project with no manual index setup.

Key invariants

  • AuthGate is the only widget allowed to swap between authenticated and unauthenticated branches. Pushed routes never replace it; logout / delete clears local state and AuthGate repaints to SignupScreen on the next frame.
  • Auth-first delete: fbUser.delete() must observably succeed before _currentUser is set to null. If Firebase Auth deletion throws (e.g. requires-recent-login), the user stays signed in with their old profile and gets a SnackBar to retry.
  • Password reset: FirebaseAuth.sendPasswordResetEmail is reachable from both the login screen and Account Settings. To avoid leaking which emails are registered, "user-not-found" returns the same generic success message as a real send.

Leave is also transactional: it finds the user's index, removes from both parallel arrays in lock-step, recomputes status (full → open if a spot frees up), notifies host and (best-effort) other joined players, and removes the user from the group chat thread. Invitee acts

The receiver opens InvitesPage (via the notification or the menu) and taps Accept or Decline.

  • Accept → re-reads invite, asserts pending + invitee identity, then delegates to OpenMatchService.joinOpenMatch. Capacity / duplicate / cancelled guards run inside that transaction. Invite status flips to accepted. Group chat membership added. Host receives an invite_accepted notification. UI routes to MatchJoinedPage.
  • Decline → status flips to declined; host receives an invite_declined notification. The match doc is not touched.

Sent-invite live count

Each row in the Sent tab subscribes to streamOpenMatch(matchId) so the "X / Y joined · N spots left" line is always honest. If the match gets cancelled, the row reads "Match cancelled"; if the match is deleted server-side, it reads "Match no longer available."

13. Messaging Architecture

Direct (1-to-1)

  • Thread id is deterministic: sort the two uids alphabetically and join with _. Finding "the thread between A and B" is a single doc read by id; no where('participantIds', arrayContains: …) query needed; duplicate threads for the same pair are structurally impossible.
  • ChatService.createOrGetDirectThread is idempotent — set(merge: true) with a payload that only fills missing fields the first time.

Group (per open match)

  • Thread id is match_<matchId>. Cannot collide with a direct id (uids never contain underscores, and the prefix is the load-bearing guarantee).
  • Thread auto-created on match create. Joiners are added via arrayUnion; leavers removed via arrayRemove. The shared createOrUpdateGroupThreadForMatch method uses union semantics on already-existing threads so a stale local snapshot cannot silently drop late joiners.
  • Group bubbles carry an optional senderName snapshot so the chat can label each message without a per-message users/{uid} read.

Single threads collection with a type discriminator

threads/{threadId}
  type: 'direct' | 'group'    (missing on legacy → 'direct')
  participantIds: [uid, uid, ...]
  lastMessage, lastMessageAt, lastSenderId, createdAt, updatedAt
  lastReadAtByUser: { uid: Timestamp, ... }
  // group-only:
  matchId, title, imageUrl, sportType, courtName

threads/{threadId}/messages/{messageId}
  senderUid, senderName?, text, sentAt

Streams

14. Unread & Read State

Rule (ChatThread.isUnreadFor(uid))

  1. If lastMessageAt == null, not unread.
  2. If lastSenderId == uid, not unread (the sender doesn't see their own message as unread).
  3. If lastReadAtByUser[uid] == null, unread (user has never opened it).
  4. If lastReadAtByUser[uid].isBefore(lastMessageAt), unread.
  5. Otherwise, read.

Where reads are bumped

ChatService.markThreadRead({threadId, uid}) is the only path that bumps a non-sender's read timestamp. It is called from exactly two places:

  • MessagePage — once at thread-open time, then on every snapshot via _maybeMarkRead (gated by _lastMarkedMessageId so per-frame snapshot deltas don't cause repeated Firestore writes).
  • GroupChatPage — same two call sites.

Visiting MessagesPage / GroupMessagesPage / UnreadMessagesPage does not clear unread state.

Write path on send

ChatService.sendMessage writes the new message under threads/{id}/messages and updates the parent thread's lastMessage, lastMessageAt, lastSenderId, and the sender's own lastReadAtByUser[senderUid] in the same batched write. Firestore deep-merges the nested map, so other participants' read timestamps are preserved.

In-app delivery

Every notification write creates a row in notifications/{id}. The notification bell streams unread count; NotificationsPage streams the full list and routes taps based on targetType + targetId.

Push delivery (two parts)

Client (PushNotificationService in this Flutter app):

  • Requests notification permission on first sign-in (iOS prompt; Android 13+ runtime permission).
  • Reads the FCM token and stores it under users/{uid}.fcmTokens via arrayUnion, supporting multi-device.
  • Listens on onTokenRefresh and re-writes after FCM rotates the token.
  • Foreground messages render an in-app SnackBar with a "View" action.

Server (functions/index.js):

  • Firestore-triggered Cloud Function on notifications/{id}.onCreate.
  • Loads the recipient's fcmTokens array.
  • Calls messaging.sendEachForMulticast with notification.title / notification.body + data.targetType / data.targetId.
  • Prunes dead tokens (NotRegistered, InvalidArgument) from the user's array.

16. Schedule Conflict Prevention

Two distinct conflicts are enforced before every write that creates or joins a session.

Court occupancy

A physical court cannot host two overlapping reservations. Sources counted as active:

  • Confirmed private bookings on the same court.
  • Non-cancelled open matches on the same court.

User schedule

A user cannot be in two overlapping active sessions, even at different courts. Sources counted as active:

  • Confirmed bookings owned by that user.
  • Matches where the user is the host.
  • Matches where the user is in joinedPlayerIds.

Overlap predicate

The canonical interval test, not exact-string equality:

existingStart < newEnd  &&  newStart < existingEnd

This correctly rejects 6:30–7:30 PM when 6–7 PM already exists, and correctly allows 7–8 PM after 6–7 PM (endpoint touch is not overlap).

Insertion points

PathGuard
BookingService.createBookingassertNoConflictForNewReservation (court + user)
OpenMatchService.createOpenMatchassertNoConflictForNewReservation (court + user)
OpenMatchService.joinOpenMatchassertNoUserConflict (user only; court is already booked by the host's match)
InviteService.acceptInviteDelegates to joinOpenMatch, inheriting the user-conflict check.

Surfaced messages

  • "This court is already booked for the selected time."
  • "You already have another booking or match during this time."

17. Court Availability

CourtAvailabilityService.availableSlotsFor(courtId, date) computes which slots from the canonical bookingSlots list are still bookable for that court and date:

  1. If the date is in the past, return empty.
  2. Load the per-court active set: confirmed bookings + non-cancelled open matches with where('courtId', isEqualTo: …).
  3. For each generated slot, skip if it overlaps any occupied interval (same overlap predicate as the conflict service) or if it's the current day and the slot has already started.
  4. Return the kept slots in canonical order.

BookCourtSheet feeds this list straight into its time grid via a FutureBuilder. The result: a user cannot tap a slot that is already booked or hosted by someone else.

  • One-time GPS capture at first MainShell render via LocationService.captureCurrent() (geolocator → geocoding).

20. Admin / Moderation

Admin gating

Hardcoded allow-list of admin emails in AdminService._adminEmails. The side drawer renders an "ID Verification Reviews" entry only for them; the admin screen re-checks on every build so a deep-linked route cannot bypass the drawer gate.

ID Verification review queue

  • Streams all users with idVerification.status == 'submitted'.
  • Each row shows the submitter's avatar, name, email, document type, legal name, ID last 4, expiry, issuing state, plus tappable chips for Document (front), Document (back), and Selfie images.
  • Approve or Reject opens an optional reviewer-note dialog and writes back to the user's idVerification.status, reviewedAt, and reviewerNote.
  • The stream auto-empties as the admin works through the queue.

Report user

From any player profile, ⋮ → Report user opens a free-text reason dialog and writes to reports/{id} with status: open. Moderator review workflow is deferred.

Feedback / suggestions

Profile → Feedback & Suggestions writes to feedback/{id} with category, message, and signed-in user snapshot. Shows a "Thank you. Your feedback has been submitted." SnackBar and clears the form on success.

22. Notable Engineering Decisions

  • Deterministic thread ids over where() lookups for both direct and group chats. One doc read by id beats a query; structurally prevents duplicate threads.
  • Snapshot fields baked into create-time writes. Host name, court image URL, sport type, etc. are written into each booking / match / invite at create time, so list cards don't need follow-up reads and historical events don't get retroactively rewritten by a profile rename.
  • Parallel arrays with index-aware rebuilds. joinedPlayerIds and joinedPlayerNames are kept in lock-step. Leave finds the index, removes from both in the same transaction. Never arrayRemove on a primitive list (it would desync).
  • Transactional concurrency. Join, leave, host-cancel, invite-accept all wrap their reads + writes in a single Firestore runTransaction; capacity / cancelled / duplicate are all asserted inside the same atomic read-write.
  • Best-effort side-effects with structured fallbacks. Notification writes, group-thread updates, and FCM token writes all catchError so a Firestore rules blip never rolls back a successful primary mutation.
  • effectiveJoinedCount = joinedPlayerIds.length + confirmedGuestCount is the single source of truth for capacity. spotsLeft, isFull, and the "+N others" placeholder all derive from it.
  • Host-cancel fanout split into two services. OpenMatchService.cancelOpenMatch notifies host + accepted players; InviteService.cancelInvitesForMatch notifies pending invitees. No overlap, so no double-notify. Cross-service circular imports are avoided by calling the invite cancellation from the UI handler after the match cancel succeeds.
  • Group thread participant union semantics. createOrUpdateGroupThreadForMatch uses arrayUnion on existing threads. Earlier code wrote a literal array under merge: true, which silently dropped late joiners — fixed by union semantics.
  • Auth-first delete. Account deletion only clears local UI state once Firebase Auth deletion has observably succeeded; otherwise the user remains signed in with their old profile.
  • Pre-flight conflict check, documented soft spot. Schedule conflict checks happen as a Firestore read pre-flight, not inside the same transaction. Documented in the Future Work section as a known soft spot for future hardening.
  • Root navigatorKey + scaffoldMessengerKey in main.dart so the push handler can route + toast without a BuildContext.

24. Future Work

The following were scoped out for this submission and are documented as opportunities for follow-up work:

  • Skill-level / rating system. Player cards still show a hardcoded 4.8 placeholder rating; a real peer-rating feature would replace this. Player level (Beginner / Intermediate / Advanced) is also future work.
  • Monetization. The Subscription screen is a UI mock; real subscriptions need a payment gateway (Stripe / RevenueCat / Apple+Google IAP).
  • Optional message on an invite. The current invite carries snapshots but no free-text message from the host.
  • Group chat participant controls. No leave-group action from inside the chat, no mute, no kick (only the host can cancel the entire match).
  • Variable-length bookings. Currently every slot is 1 hour; totalPrice is always pricePerHour. A multi-hour selector would multiply by hours.
  • Schedule conflict hardening. Move the conflict check into the same Firestore transaction as the write, or back it with a "court-day-slot" lock document, to close the small TOCTOU window.
  • Geo-bounded user query. streamAllUsers is an unfiltered collection scan, sorted client-side; suitable for a class project, not for scale.
  • Court seeding promotion. Currently a debug-only assert(...) block — should move to a one-shot CLI / Cloud Function for production.
  • Profile fields not displayed. age and postalCode are persisted but never displayed.
  • Notification archive. Only mark-as-read exists; no delete / archive.
  • APNs auth key for production iOS push. Set up in the Firebase console before iOS push can deliver outside the simulator.
  • Server-side authoritative moderation. Reports are persisted but the moderator workflow (review, suspend, ban) is out of scope. Same for idVerification rejections.

25. Setup & Deployment Guide

Prerequisites

  • Flutter SDK installed.
  • Firebase CLI: npm install -g firebase-tools.
  • FlutterFire CLI: dart pub global activate flutterfire_cli.
  • A Firebase project; an Apple developer account if shipping to iOS.
  • A Cloudinary account (free tier is enough).

One-time setup

# Wire FlutterFire into the project (regenerates firebase_options.dart)
flutterfire configure

# Configure Cloudinary
# Edit lib/core/cloudinary_config.dart with your cloudName + uploadPreset.

# Install Flutter dependencies
flutter pub get

Run on a simulator / device

flutter run

Deploy the Cloud Function (push sender)

cd functions
npm install
firebase login
firebase use --add        # pick the RallyUp project
firebase deploy --only functions

After this deploy, any new doc written to notifications/{id} triggers the function and the recipient's devices receive a push.

Optional

  • iOS push: upload an APNs auth key in the Firebase console (Project Settings → Cloud Messaging).
  • Android push: google-services.json in android/app/ is enough.
  • Admin email: edit the allow-list in lib/services/admin_service.dart.

26. Comparison with the Reference Project

The CSEN268 reference project (santa-clara) is a course-template scaffold with 37 commits and a README that mostly explains how to wire FlutterFire. Its documentation index lists ten short docs covering App Structure, Theme, GoRouter, Bottom Navigation, Authentication Bloc, Firebase UI Auth, Firestore, Authentication Repository.

RallyUp's submission is a fully implemented product on the same stack:

  • 30,000+ lines of production-shaped Dart.
  • 10 live Firestore collections.
  • Transactional Firestore writes for join, leave, accept, cancel.
  • Real-time direct and group chat with deterministic ids and unread tracking.
  • Push notifications wired to a Firebase Cloud Function.
  • An in-app admin moderation surface for ID verification.
  • Cross-cutting schedule-conflict prevention that spans bookings, matches, invites, and joins.

The biggest qualitative difference is that RallyUp's primitives (booking, match, invite, chat, notification) all share one consistent data model with one set of conflict and concurrency invariants. The reference scaffold is a starting point; RallyUp is the destination.
